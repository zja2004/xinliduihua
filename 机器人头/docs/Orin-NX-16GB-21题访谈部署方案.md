## 2. 最终采用的技术组合

**保留现有项目，不从头改成 Ollama + Qwen3 + Paraformer + VITS。** 新需求主要缺的是流程、音频工程和记录管理，不是再下载一组模型。

| 模块 | 第一版选择 | 实现状态与理由 |
| --- | --- | --- |
| LLM | Qwen3.5-4B-Q4_K_M | 当前 baseline，资产已在开发电脑下载；原始模型卡标注 Apache-2.0，转换及其余资产许可仍单独核对 |
| 推理运行时 | llama.cpp `b11669`，CUDA，架构 87 | 项目已有目标机编译脚本，不安装另一套常驻推理服务 |
| ASR | sherpa-onnx `1.13.8` + 中文 streaming Zipformer small CTC INT8 | 保留已有模型；已确认 PyPI 有该版本的 Python 3.10 ARM64 wheel，尚未在板上验证推理 |
| TTS | Kokoro v1.1-zh INT8，现有中文音色 | 保留已有声音链路；逐句合成和可中断播放仍需新增 |
| VAD / 端点 | VAD + ASR 端点 + 用户显式完成指令 | VAD 模型及阈值在 P1 固定；不能只凭一次静音直接跳题 |
| 回声消除 | 先耳机测试；扬声器阶段引入 WebRTC AEC3 | AEC3 需要独立集成与验收；当前 PulseAudio 有音频服务不代表已有 AEC3 |
| 视频 | GStreamer + `nvv4l2h264enc` + 分段封装 | CPU 不承担常规 H.264 软件编码；实际支持格式以插入的摄像头为准 |
| 流程与界面 | Python 确定性状态机；后续增加 FastAPI 和本机网页 | 目前项目没有这些访谈 API 和界面 |
| 数据 | SQLite + 分段媒体 + JSON/文本导出 | 当前尚未实现正式访谈数据存储 |

实验组仍保留 `empero-ai/Qwen3.8-4B-Distill`，它是社区模型，不是 Qwen 官方 3.8-4B。只在完成 P0 后顺序 A/B；不与 baseline 同时加载，不默认用于真实学生。

**不需要多 Agent，也不先微调。** 状态机负责题序、跳过、暂停和写入；模型只在受限接口内理解回答、提出允许的追问和形成有依据的摘要。只有确认了具体模型能力缺口并准备好授权、去标识化且有独立测试集的数据后，才讨论微调。

## 3. 系统结构与权限边界

```text
本机网页 / 工作人员控制台
             │
访谈状态机 ──┼── SQLite 事务 / 会话日志 / 导出器
     │       └── 媒体时间戳与问题片段索引
     ├── 本地 LLM 服务（127.0.0.1:18080，只常驻一组）
     ├── TTS 分句合成 → 可取消播放队列 → 实际播放参考 → AEC3
     └── 麦克风持续采集 → AEC3 → VAD/ASR → 稳定转写/控制意图

摄像头 → GStreamer 硬编码 → 短媒体分段 → 按问题导出
```

- 实际音频采集只由一个音频引擎管理，ASR、AEC 和录音共享有时间戳的帧；不要启动多个互相争抢设备的录音程序。
- 采集回调只搬运数据，使用有上限的缓冲队列；LLM、合成、编码、数据库写入不放进音频回调。
- 媒体进程可用系统 `/usr/bin/python3` 和 GObject Introspection；应用及模型在项目 `.venv`。普通 venv 不会自动继承系统 `python3-gi`，不要假设安装系统包后就能在 venv 中 `import gi`。
- 所有进程使用同一台机器的单调时钟，并记录音频采样序号、视频 PTS 与会话时间零点的映射；墙上时间只用于审计，不用于切片对齐。
- 设备、数据库和文件系统操作由应用执行；LLM 不获得 shell、任意路径、任意 SQL、联网或自动通知权限。
- 后续网页服务默认 `127.0.0.1:18088`。从电脑管理时使用 SSH 隧道；不默认向整个局域网开放录音、录像或档案接口。

## 4. 第一阶段：部署现有原型到这块板子

以下是**后续执行命令**，本次生成方案时没有执行复制、安装、编译或模型启动。

### 4.1 在开发电脑复制代码和已校验模型

只传白名单目录，不传开发电脑的 `.venv`、`.runtime`、报告、真实会话、密码或其他个人目录。不要使用 `--delete`。

```bash
ssh nvidia@192.168.3.222 'mkdir -p /home/nvidia/psych-interview'
cd '/home/koliuhiks/桌面/projects/心理模型'
rsync -a --info=progress2 --exclude='__pycache__/' --exclude='*.egg-info/' src scripts configs models tests pyproject.toml README.md nvidia@192.168.3.222:/home/nvidia/psych-interview/
```

复制完成后用资产清单中的 SHA256 核验 GGUF；语音资产沿用现有 `models/receipts/` 记录，并核对解包后的必需文件。校验不能只比较文件名。模型下载和安装依赖允许联网；访谈运行阶段才要求不依赖外网。

### 4.2 在开发板准备环境并编译

管理员只补齐缺少的包，密码在开发板或 SSH 终端输入。不要运行整体 `apt upgrade`，不要混装桌面 CUDA 包或替换 JetPack 驱动。遇到 apt 锁等待现有进程结束，不删除锁文件。

```bash
sudo apt-get -o DPkg::Lock::Timeout=180 install --no-install-recommends v4l-utils ffmpeg
cd /home/nvidia/psych-interview
export PATH="/usr/local/cuda/bin:$PATH"
bash scripts/bootstrap.sh
bash scripts/build_jetson.sh
.venv/bin/orin-voice doctor
```

若 apt 索引过期，先由管理员刷新索引再重试安装，不借机升级整套系统。构建脚本固定 `b11669`、`GGML_CUDA=ON`、架构 87、`-j2`；它拒绝错误架构或不同的既有源码版本。不要在 Orin 上使用 `scripts/install_llama.py --cuda`，那个入口下载的是 x86 桌面运行库。

现有 bootstrap 的部分依赖是版本区间。P0 成功后应在板上另存一份 ARM64 依赖锁定清单和 wheel 缓存，不能把开发电脑的 `requirements-host.lock.txt` 当作已验证的目标机环境。

### 4.3 先完成无摄像头、无真实录音的检查

```bash
cd /home/nvidia/psych-interview
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/orin-voice voice-smoke
.venv/bin/orin-voice ask --profile baseline --ctx-size 2048 --max-tokens 96 '你好，请用一句话介绍你能提供的支持。'

```

验收时检查 `.runtime/server-*.log` 是否确实启用了 CUDA/GPU offload，同时记录 `tegrastats`。能得到回答不等于用了 GPU；`voice-smoke` 只证明合成 WAV → ASR 的文件链路，不证明麦克风、扬声器或完整响应延迟。

### 4.4 外设接入后再开麦

建议先用 UVC USB 摄像头与一套可同时录放的 USB 音频设备；第一轮使用耳机，扬声器留到 AEC 验收。这里不指定尚未核验兼容性的商品型号。

```bash

arecord -l
aplay -l
pactl list short sources
pactl list short sinks
```

确认设备身份后，才由现场测试者明确开始录音、播放和摄像测试；摄像头路径优先使用实际存在的 `/dev/v4l/by-id/`。不要把 `hw:0,0`、默认 APE 或显示器 HDMI 输出直接当成目标麦克风/扬声器。

现有项目的手动闭环入口为：

```bash
cd /home/nvidia/psych-interview
.venv/bin/orin-voice talk --profile baseline --ctx-size 2048 --max-tokens 96
```

这仍是按键录音和转写确认模式；完成它只是 P0，不得标记为“全双工 21 题系统上线”。

## 5. 全双工与打断的具体实施

### 音频链路

1. 优先按实际声卡支持的采样率建立稳定的连续采集和播放；若使用 48kHz、10ms 音频块，则每块 480 个采样。不要强迫不支持该格式的声卡运行。
2. AEC 获得与麦克风帧正确对齐、经过播放侧重采样和增益处理的参考帧，并估计实际输出延迟；参考不能仅使用尚未播放的整段 TTS 文件。
3. 清理后的单声道音频重采样到当前 ASR 所需的 16kHz；持续保留短暂的内存 pre-roll，避免打断时丢失第一个字。
4. VAD 候选发言触发“尽快停止 AI 出声”；ASR 的稳定结果再确定重复、跳过、暂停、停止或普通回答意图。噪声不应直接变成已回答状态。
5. 每一轮发声分配 `generation_id`。打断同时停止播放、清空待播 PCM、取消或丢弃旧 LLM/TTS 任务结果，防止几秒后继续播出旧回答。
6. 首句文本形成后即排队合成，限制句长和队列长度。当前 Kokoro 集成不是音频 token 流式模型，第一版做“逐句合成 + 逐句播放”，不宣称模型原生流式 TTS。

### 端点与安全要求

- 初始设计参数：约 150–250ms 连续人声作为打断候选，约 800–1200ms 静音作为回答结束候选；均需实测调整，慢说话和情绪性停顿应获得更长等待。
- 支持“我说完了”“再说一遍”“暂停”“跳过”“停止录制”；重复问题不增加题号，跳过保留记录。
- 有 ASR 歧义时澄清；涉及否定、人物、时间和安全相关表述时回读确认，不能自动补写含义。
- 扬声器阶段分别测试仅 AI 发声、仅人声、双讲、噪声和不同音量。没有 AEC 双讲测试结果，就保留耳机模式，不把 VAD 单独称为全双工完成。
- 当前板子使用 PulseAudio，不直接照抄 PipeWire 配置；PulseAudio 的 WebRTC 回声消除模块也不能未经版本核验就称为 AEC3。确定 AEC3 路线时固定 WebRTC 源码版本及原生音频模块构建产物。

## 6. 21 题访谈状态机

题目由经负责人确认的配置提供：`questionnaire_id`、`version`、内容哈希和恰好 21 个唯一题目 ID。**目前没有收到正式 21 题，不能自行编题、假定它是某个临床量表，或生成量表分数。**

会话状态：

```text
PRECHECK → NOTICE → CONSENT_PENDING → INTERVIEW → REVIEW → SUMMARY → COMPLETED
                                ↘ DECLINED
INTERVIEW ↔ PAUSED
任意活动状态 → STOPPED / NEEDS_HUMAN_SUPPORT / RECOVERY_PENDING
```

每题状态：`PENDING → ASKING → LISTENING → CLARIFYING → ANSWERED`；允许进入 `SKIPPED` 或 `INTERRUPTED`。追问可直接返回 LISTENING；是否结束由确定性规则、用户明确确认和必要的人工确认共同控制，不由 LLM 自行推进。

| 输入/情况 | 必须发生的行为 |
| --- | --- |
| 再说一遍 | 留在当前题，重播核准问题，不新建答案 |
| 普通回答 | 保存原始转写及片段关联，必要时追问至多一次 |
| 不想回答 / 跳过 | 标记 SKIPPED，不代填答案，不反复施压 |
| 暂停 | 停止持久化录音录像，记录间断；恢复前再次提示 |
| 停止录制 | 先停止采集/写入，后确认保存、删除或交工作人员处理 |
| 识别不清 | 澄清或标记无法识别，不把静音当成完成 |
| 出现需要现实支持的线索 | 暂停正常访谈，进入人工支持流程；无真实通知回执不得说“已经通知老师” |
| 断电或进程异常 | 标记中断，重启后由工作人员确认恢复；不自动继续拍摄 |

LLM 只能返回通过 schema 验证的有限字段，例如 `intent`、`needs_clarification`、`candidate_followup`、`evidence_refs`。题号、允许状态迁移、最大追问数、数据库路径都由程序检查。题目完成数不包含 SKIPPED；另设 `processed_count = answered_count + skipped_count`，避免“处理完 21 题”被误写成“回答了 21 题”。

预设题目、欢迎语、同意说明、重复和跳过确认语提前用 TTS 生成并校验缓存。固定问题直接播放缓存，不每题都调用 LLM；这样减少延迟、资源占用和措辞漂移。

## 7. 音视频和结构化结果保存

### 存储布局（待实现）

```text
/home/nvidia/psych-interview-data/
  interview.sqlite3
  sessions/<随机会话ID>/
    manifest.json
    answers.json
    summary.txt
    media/segment-000001.mp4
    media/segment-000002.mp4
    audio/answer-Q01.wav
    exports/Q01.mp4
```

- 会话目录权限 0700、普通数据文件 0600；姓名和学号不进入文件名。身份信息与访谈内容分开授权管理，默认不采集不必要标识。
- 在明确同意后开始持久化。摄像头持续运行并按短片段封装，不为每题重启摄像头；暂停和停止必须真正停止存储，不只是暂停提问。
- 初始录像设计：720p、25fps、H.264，目标约 3Mbps，以实际摄像头格式和实测硬编能力调整。约每 10 秒请求分段，约 1 秒关键帧间隔为初始设计值，不保证任意时刻精确切断。
- GStreamer 分段与关键帧存在边界约束。精确的每题开始/结束时间保存在索引中；需要精确 MP4 导出时解码并重编码边界或片段，不把 `ffmpeg -c copy` 当作任意毫秒精确裁切。
- 完整会话视频优先作为分段和索引的逻辑集合；只有显式导出时才合并为 `full_session.mp4`。避免默认同时永久保存全场、全部分段和全部题目副本。
- 原始麦克风、AEC 后音频及播放参考的长期保留属于可选调试项，需要单独授权和期限；常规模式只保留业务必需的片段，不默认保存全部敏感原始材料。

### 数据一致性

SQLite 至少有 `sessions`、`questions`、`answer_segments`、`events`、`media_segments`、`exports`、`review_tasks`。每个动作使用唯一事件 ID；重试不重复计数。ASR 原文、人工/用户确认文本和摘要分别保存，不能让模型覆写原文。

每题通过事务提交状态和答案；媒体文件完成封装、必要的同步和校验后才标记为可用。JSON 采用临时文件加原子替换，并在需要断电可靠性的路径同步文件和目录；JSON 是可重建导出，不是另一套互相竞争的主数据库。

`answers.json` 必须保留全部 21 题，包含题目版本、状态、片段 ID、会话相对时间、原始及确认文本、追问、跳过原因、证据引用和人工审核状态。恢复时校验已有分段，未完成片段标记损坏/缺失，不伪造完整视频。

以 3Mbps 估算，视频约 1.35GB/小时；16kHz 单声道 16-bit PCM 约 115MB/小时。这是容量计算，不是实测文件大小。若增加原始多路录音及导出副本，单场占用会明显增加。暂定保留至少 30GB 空闲空间，接近阈值拒绝开启新场次并提示人工处理，不静默删除学生档案。

## 8. 心理相关分析的边界

- 摘要只引用已确认回答，输出 `evidence_refs` 对应题目、回答片段和时间。缺失信息标记为未知；不能从沉默、摄像头画面或语气直接下诊断。
- “心理筛查”须在明确题目、授权、适用人群、核准计分规则和专业审核流程后单独实现；当前 21 题访谈不能自动等同于标准化筛查。
- 第一版的“情绪识别”限定为对自述的描述与待确认线索；声学情绪分类或视觉情绪推断是独立实验，不作为危机或临床判断依据。
- 心理科普使用经过审核、带版本和出处的本地资料库；检索不足时说明不知道，不让模型编造诊断和治疗建议。
- 危机线索规则只是进入人工复核的候选触发器。上线前必须配置现实联系人、适用时间、通知回执、失败回退和现场处置责任；模型不得自行承诺已呼叫帮助。
- 真实学生使用前，由项目负责人落实录制告知、同意/拒绝、未成年人相关授权、保存期限、访问审批、导出与删除制度。开发验收仅用合成材料或明确同意的测试者。
- 生产数据要有加密、密钥保管和可恢复备份方案。全盘加密、数据库加密和媒体加密是不同层次；本次未实施，不能把“本地离线”称为已经加密或合规。
- 访谈前端与档案管理界面分权；不在浏览器控制台、服务日志或错误栈中打印完整敏感回答。实际接触学生之前，应建立更换默认口令、账户权限和备份验证的部署清单。

## 9. 内存、并发与性能预算

以下均为需要真机测试的工程目标，不引用开发电脑 RTX 显卡结果作为 Orin 性能。

- 单用户、单 LLM、ASR/TTS 各一套；初测上下文 2048，普通回复 96–128 token。稳定后再考虑 4096；21 题历史由数据库和受控摘要管理，不把整场无限追加到上下文。
- 希望整机峰值占用控制在约 11–12 GiB，保留约 3 GiB 以上余量；实际模型缓存和线程工作区必须测量，不以 GGUF 文件大小替代运行内存。
- 编译并发保持 2；推理线程与 ASR/TTS 并发按采集丢帧、CPU 和延迟调整。先减少上下文、输出和队列积压，不把 swap 当作额外 GPU 显存。
- 热模型、固定条件下，打断至扬声器停止出声的目标为 p95 ≤ 500ms；用户实际结束说话至第一段回复真正出声，先争取中位数约 2 秒，另报 p95。未达到时按端点/ASR/LLM/TTS/播放分段定位，不能只报首 token。
- 记录冷启动、首 token、首句文本、首句 PCM、扬声器实际出声、ASR 端点、峰值内存、温度、功耗和掉帧。播放开始的应用时间戳只是近似，正式验收需要回录或外部测量。
- 40W 是本次读到的配置，不是无条件推荐。确认原配供电、散热器、风扇和载板能力后做持续负载测试；本方案不自动调高功耗或锁最高频率。

## 10. 实施顺序和验收门槛

| 阶段 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| P0 | 现有模型迁移、GPU 推理、实际录放 | 断开外网后完成真实语音问答；文件合成测试与麦克风测试分别记录 |
| P1a | 耳机条件下持续收音、分句播放、取消任务 | 打断后不继续播放旧语音；重复/暂停不丢失当前题 |
| P2 | 21 题状态机、题库校验、SQLite | 全部回答、跳过、拒绝、重说、追问、异常重试都不漏题、不重复计数 |
| P3 | 摄像头、分段录像、音画时间对齐 | 每题与对应音视频一致；暂停不录制；断电后已封装片段可恢复 |
| P1b | 扬声器条件下的 AEC 和双讲 | 仅 AI 发声不误推进题目；人声插入可打断且首字不丢失；失败回退耳机 |
| P4 | 有依据的总结、语音播报、导出与人工复核 | 摘要可追溯，无伪造答案/诊断/分数/通知；权限和删除流程可验证 |
| P5 | 启停服务、稳定性、安全和恢复 | 断网/磁盘不足/声卡拔出/ASR 超时/LLM 异常/断电均有可审计行为 |

P2 与录像开发不必等待扬声器 AEC 完美，但“扬声器全双工完成”的标签必须等 P1b 验收。先测试 2 小时连续运行及多次完整模拟访谈，再做更长耐久测试；这些时长是拟定门槛，不是已经通过的成绩。

端点、打断、题库、恢复、证据引用要有自动化测试；声音听感、现场打断、设备表现和心理内容仍需要人在实际设备上验收。现有单元测试只覆盖原型的一部分，不能代表新增模块通过。

## 11. 代码扩展与运维计划

保留现有 `src/orin_voice/` 和 CLI。后续增加独立访谈包，按职责划分：`questionnaire`、`state_machine`、`audio_engine`、`turn_manager`、`recorder`、`storage`、`summary`、`api`，分别配套测试；这些文件本次没有创建，也没有可运行的 21 题启动命令。

API 规划仅包含开始/暂停/恢复/停止会话、只读状态、授权查看/导出和工作人员审核。状态迁移由后端强制校验；网页不能直接指定磁盘路径或发送任意 LLM 工具调用。

桌面原型先采用手动启动，确认稳定后再配置用户服务。llama.cpp 常驻一个实例，不为每个问题重新加载；视频工作进程只在同意后启动。系统重启可以恢复管理界面，但不能自动恢复摄像或收音。

应用完成后，可在电脑上用下面的隧道访问板子的本机界面；**当前尚无服务监听 18088**：

```bash
ssh -N -L 18088:127.0.0.1:18088 nvidia@192.168.3.222
```

浏览器使用本地地址 `http://127.0.0.1:18088`。不要向整个局域网开放未认证的控制接口。浏览器安装、账户登录与访谈数据均不依赖云端 LLM；外网检索不是运行期必要条件。

## 12. 现在可以推进什么，还缺什么

可以立即实施：P0 的项目同步、ARM 环境安装、llama.cpp 编译、无真实录音的文件链路测试。仍需现场补齐：

1. 摄像头与实际音频设备；接入后确认型号、格式、采样率和稳定设备标识。
2. 正式的 21 道题、题目版本、是否允许追问/改写/跳过，以及访谈语言。本方案暂按中文设计。
3. 若面向真实学生，明确数据负责人、保留/删除规则和现实人工支持流程。

在这些信息补齐前，可用明确标记为合成的题目测试状态机，但不能把占位题或原型提示词包装成已验证的心理筛查产品。
